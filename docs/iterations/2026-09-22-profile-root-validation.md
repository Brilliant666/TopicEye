# Profile root validation: diagnostics and candidate assembly

## Scope

Fix lost root-level Profile validation reasons and two deterministic assembly
defects and a capability-filter false positive found in a fixed production cohort. No ranking, budget, retry, lock,
schema acceptance, source refresh or model configuration changes.

## Findings

- Official positioning selection could promote a flattened development table
  or a blockquoted slogan over a valid, evidence-bound assessment.
- The role recognizer omitted concrete storage/compute separation and
  component/action/object mechanisms, despite requiring a mechanism or outcome
  in the final Profile contract.
- Material diagnostics retained Pydantic location/type but discarded all
  messages, making distinct object-level checks indistinguishable.
- Product component packaging was rejected solely because its delivery prose
  mentioned installation/deployment. A bounded structural exception preserves
  component relationships, while commands, operation titles and invalid refs
  remain rejected.

Saved source/stage cache replay (not original Provider response replay) reproduced
the root rejection for ZCode and HydraDB. Their existing cached assessments or
official translations support zero-model isolated reconstruction after the fix.
NiubiGEO lacks the failed assessment response/cache; source-only reconstruction
reproduces its blockquoted slogan rejection, not the complete original model run.

Other cohort failures remain separate: a repository-metadata HTTP301 and an
invalid model translation without its original response. Financial-services'
saved translations reproduce capability filtering and reconstruct a valid
Profile after the bounded filter fix, in scratch without its negative ledger.
This is not a production retry or permission to remove that ledger. Its selected
positioning remains the evidence-bound disclaimer/outcome paragraph; passing
validation does not imply that source selection has become ideal. Its production
nonretryable content record remains a separate re-evaluation constraint.

## Contract

Known, fixed validation literals map to reviewed stable rule codes and safe
explanations. Unknown messages remain unknown. No input, error context, response,
prompt, credentials or arbitrary exception text is persisted. Root `loc=[]`
remains root-level. Existing error type and business failure classification are
unchanged. Diagnostics use the existing attempt persistence path; old records
are not rewritten. A diagnostic failure cannot replace the business exception.

Candidate rejection preserves source evidence and cache identities. Valid
assessment fallback and strict evidence validation remain authoritative. No
repository-specific allowlist or forced ready/complete state is added.

## Validation and runtime boundary

Focused regressions cover fixed/custom/unknown reasons, redaction, historical
record compatibility, actual failure capture and disk readback, candidate noise,
mechanism recognition, and healthy prior positioning cases. CI remains required.
Private production snapshots and outputs are kept outside Git.

The production single-project entry performs a source request and respects daily
failure admission. All six affected items had exhausted their current daily
failure limit; no counter reset, manual regeneration, or ad-hoc cache write is
authorized by this patch. A deployed code fix is not a claim of restored content.
Subsequent natural processing must validate the actual saved Profile and formal
API/HTML. Existing complete materials and original failure/consumption records
must survive. Code rollback preserves business data and prior diagnostics.
